# 프로젝트 정책

## 목적

Capacity Planner는 제조 작업 데이터를 안전하게 보존하면서 BAY별 작업 진행률, 작업자,
이슈 및 운영 상태를 역할에 맞게 관리하는 서비스입니다.

정책은 UI 편의를 위한 지침이 아니라 서버에서도 반드시 검증해야 하는 비즈니스 규칙입니다.

## 핵심 원칙

- 작업 상태는 `미작업 → 작업 중 → 작업 완료` 방향으로만 진행합니다.
- 작업자는 자신이 시작한 작업만 완료할 수 있습니다.
- 작업자는 작업 시작을 취소하거나 완료 상태를 되돌릴 수 없습니다.
- 잘못된 상태 변경은 Manager 또는 Admin이 사유를 기록한 뒤 교정합니다.
- 작업 취소와 무효화는 물리 삭제가 아닌 감사 가능한 상태 및 이벤트로 보존합니다.
- 고소작업은 색상만으로 표현하지 않고 아이콘과 텍스트로 명확하게 표시합니다.
- 권한과 상태 전이 규칙은 클라이언트와 서버에서 모두 확인하며, 서버 검증을 최종 기준으로
  삼습니다.
- 외부 CDN 의존을 최소화하고 폰트, 아이콘, UI 라이브러리는 애플리케이션 빌드에 포함합니다.

## 역할과 권한

### Admin

- 모든 BAY와 작업을 조회합니다.
- BAY, BAY 템플릿 및 사용자 계정을 관리합니다.
- 작업 시작, 완료, 시작 취소, 완료 복원 및 작업 무효화를 처리합니다.
- 전체 작업 상태 이력과 이슈를 확인합니다.
- Telegram 알림 설정과 전송 이력을 관리합니다.
- 운영 시간을 수동으로 닫거나 연장할 수 있습니다.

### Manager

- 모든 BAY의 현황과 작업을 조회합니다.
- BAY와 BAY 템플릿을 생성하고 초기 작업 구성을 관리합니다.
- 작업을 시작하고 완료할 수 있습니다.
- 잘못 시작한 작업을 사유와 함께 취소할 수 있습니다.
- 완료된 작업을 정책 범위 안에서 복원할 수 있습니다.
- 작업 무효화는 허용된 범위에서만 수행합니다.
- Worker 계정을 관리할 수 있습니다.

초기 버전에서 Manager는 전체 BAY를 관리합니다. 팀이나 BAY별 담당 범위가 필요해지면 별도의
팀 구성원 및 BAY 할당 모델을 추가합니다.

Admin과 Manager는 `/admin` 경로의 동일한 관리 콘솔을 사용합니다. 역할 차이는 별도 화면을
복제하지 않고 메뉴, 액션 및 서버 API 권한으로 제한합니다.

### 운영 시간 연장

- Admin과 Manager는 정규 운영 시간이 아닐 때 작업 운영을 30분 또는 60분 연장하거나,
  종료 시각을 직접 지정할 수 있습니다.
- 직접 지정하는 종료 시각은 한국시간을 기준으로 표시하며 현재보다 미래여야 합니다.
- 한 번의 연장은 요청 시점으로부터 최대 24시간까지 설정할 수 있습니다.
- 분 단위 연장과 직접 지정 종료 시각은 동시에 요청할 수 없습니다.

### Worker

- 허용된 BAY의 작업을 검색하고 조회합니다.
- 미작업을 시작하고 자신이 시작한 작업을 완료합니다.
- 작업 시작 취소, 완료 복원, 작업 무효화는 수행할 수 없습니다.
- 자신의 작업 이력을 기준으로 운영 정보를 확인합니다.

## 작업 상태 정책

| 상태      | 내부 값       | 설명                      |
| --------- | ------------- | ------------------------- |
| 미작업    | `not_started` | 시작 가능한 작업          |
| 작업 중   | `in_progress` | 특정 사용자가 시작한 작업 |
| 작업 완료 | `completed`   | 작업이 완료된 상태        |

### 작업자 상태 전이

| 작업 | 이전 상태     | 다음 상태     | 조건                                                |
| ---- | ------------- | ------------- | --------------------------------------------------- |
| 시작 | `not_started` | `in_progress` | 운영 가능 시간이며 아직 다른 사용자가 시작하지 않음 |
| 완료 | `in_progress` | `completed`   | 현재 사용자가 시작한 작업                           |

- 상태 변경은 조건부 UPDATE와 상태 이벤트 INSERT를 하나의 DB 트랜잭션으로 처리합니다.
- 동일 작업을 동시에 시작하면 한 요청만 성공해야 합니다.
- 동시성 충돌은 HTTP `409`와 명확한 충돌 메시지로 반환합니다.

### 관리자 교정

- 시작 취소는 Manager 또는 Admin만 수행합니다.
- 시작 취소 시 사유가 필수이며 `cancel_start` 이벤트를 남깁니다.
- 완료 복원은 허용된 관리자 역할만 수행하며 `restore` 이벤트를 남깁니다.
- 작업 무효화는 데이터를 삭제하지 않고 무효화한 사용자, 시각, 사유를 기록합니다.

## 작업 시작 확인

작업 시작은 작업자가 직접 되돌릴 수 없는 동작이므로 전역 확인 UI를 거칩니다.

- BAY 코드
- 작업명
- 상세 작업
- 품번
- 고소작업 여부

고소작업이면 안전 구분을 확인할 수 있는 안내를 추가합니다. 확인창은 시작 후 관리자에게만
취소를 요청할 수 있다는 점을 명시합니다.

## 고소작업 정책

- 고소작업 단위는 상세 작업입니다.
- 템플릿 행과 실제 작업 행에 `isHighAltitude`, `safetyNote`를 저장합니다.
- 템플릿 편집, BAY 생성 검토, 작업 검색 결과, 시작 확인, 진행 중 작업, 관리자 상세 및
  집계 화면에서 식별할 수 있어야 합니다.
- 배지는 아이콘과 `고소작업` 텍스트를 함께 사용하며 색상만으로 의미를 전달하지 않습니다.

## 작업자 경험

- BAY를 선택한 뒤 BAY 내부 작업을 검색합니다.
- 검색 대상은 BAY 코드, 작업명, 상세 작업, 품번, 품명, 업체입니다.
- 미작업, 작업 중, 고소작업, 이슈 여부로 필터링할 수 있습니다.
- 시작 가능한 미작업을 기본 우선순위로 둡니다.
- 서버 검색은 debounce와 cursor pagination을 사용하며 기본 조회 단위는 30건입니다.
- 결과에는 BAY, 작업명, 상세 작업, 품번과 품명, 상태, 고소작업 및 이슈 여부를 표시합니다.

## 관리자 대시보드

Admin과 Manager는 1개 이상의 BAY를 한 화면에서 관리할 수 있어야 합니다.

주요 지표:

- 전체 BAY 수
- 미작업, 작업 중, 작업 완료 수
- 열린 이슈와 이슈가 있는 BAY 수
- 진행 중인 고소작업 수
- 오늘 시작 및 완료한 작업 수
- 마지막 갱신 시각

BAY별로 완료율, 상태별 작업 수, 열린 이슈, 고소작업, 현재 작업자 및 최근 활동을 제공합니다.
검색과 진행 상태, 이슈 및 고소작업 필터를 지원합니다.

## BAY 생성 정책

- Admin과 Manager가 BAY와 BAY 템플릿을 생성할 수 있습니다.
- 템플릿은 BAY 생성 시점의 초기 데이터 원본입니다.
- 생성 전 복사된 작업 행은 수정할 수 있습니다.
- BAY와 작업 행은 하나의 트랜잭션으로 저장합니다.
- 생성된 BAY와 원본 템플릿은 이후 서로 독립적입니다.
- 템플릿 변경을 기존 BAY에 소급 적용하지 않습니다.
- 클라이언트 검증과 별개로 서버에서 입력을 다시 검증합니다.

## 이슈 및 Telegram 정책

- Admin, Manager, Worker는 작업 상세에서 심각도와 내용을 입력해 이슈를 등록할 수 있습니다.
- 이슈를 PostgreSQL에 먼저 저장한 후 Telegram 전송을 처리합니다.
- Telegram 실패로 이슈 저장을 롤백하지 않습니다.
- 이슈 저장과 Outbox 생성을 동일한 트랜잭션에서 처리합니다.
- 일시적인 네트워크 오류, Telegram `429`, `5xx`는 최대 5회까지 재시도합니다.
- 영구 실패와 제외 항목은 Admin이 원인을 확인하고 재처리할 수 있어야 합니다.
- Bot Token은 암호화해서 저장하고 조회 시 원문을 반환하지 않습니다.

## 데이터 안전

- 원본 Excel, CSV, TSV, DB dump, 로컬 SQLite 및 업로드 파일을 저장소에 커밋하지 않습니다.
- 운영 데이터는 PostgreSQL에 저장하고 저장소에는 스키마, migration 및 코드만 둡니다.
- `.gitignore`에서 `data/`, `uploads/`, `*.xlsx`, `*.csv`, `*.db`, `*.dump` 등을 차단합니다.
- 비밀키, 서비스 역할 키, Bot Token 및 실제 환경 파일을 커밋하지 않습니다.
- 작업 데이터는 hard delete보다 상태 변경과 감사 이력을 우선합니다.

## 정적 자산 정책

- Google Fonts를 포함한 외부 폰트 CDN을 사용하지 않습니다.
- 폰트는 npm 패키지 또는 자체 호스팅 WOFF2로 제공합니다.
- 아이콘과 UI 라이브러리는 고정된 npm 의존성으로 빌드에 포함합니다.
- 차트가 필요하면 초기에는 CSS 기반 시각화를 우선하고, 라이브러리가 필요할 때도 CDN 대신
  npm 패키지를 사용합니다.

## 개발 정책

### 포맷

- Prettier 설정은 `.prettierrc.json`을 기준으로 합니다.
- 세미콜론 없이 작은따옴표, 공백 2칸, 최대 100자, LF 줄바꿈을 사용합니다.
- 여러 줄 구조에는 가능한 범위에서 trailing comma를 사용합니다.
- 변경 파일은 반영 전에 Prettier와 `git diff --check`로 검사합니다.

```bash
pnpm exec prettier --write <files>
pnpm exec eslint <files>
git diff --check
```

### 커밋

- 서로 다른 작업 영역은 별도 커밋으로 분리합니다.
- 커밋 메시지는 `<type>(<scope>): <description>` 형식을 사용합니다.
- 기능 브랜치는 `main`에 non-fast-forward 방식으로 병합해 작업 및 merge 이력을 보존합니다.

```text
feat(component): 메인 UI 생성
feat(bay): BAY 생성 기능 구현
chore(db): PostgreSQL 및 인증 설정 완료
chore(rule): 프로젝트 개발 지침 설정
docs(readme): 프로젝트 문서 정리
```

## 인수 기준

- Worker는 순방향 상태 전이만 수행할 수 있습니다.
- API를 직접 호출해도 권한 없는 역방향 변경이 거부됩니다.
- 동일 작업 동시 시작 시 하나의 요청만 성공합니다.
- 관리자 교정에는 사유와 감사 이력이 남습니다.
- 고소작업은 검색, 상세, 확인창 및 관리자 화면에서 텍스트로 식별됩니다.
- 작업 검색과 pagination 결과가 일관되어야 합니다.
- 작업 데이터는 취소 또는 무효화 이력과 함께 보존됩니다.
- 정적 자산은 외부 Google Fonts CDN 없이 로드됩니다.
